# 轻量索引 vs 完整 RAG：取舍结论

## 现状与实测基线

真实 vault（`D:\download\ratio`）规模：

- 44 个 Markdown 文件（排除 `.git`/`.obsidian`），约 13 个文件使用 tags、9 个使用 aliases；
- 结构高度规整：frontmatter（`document_type`、`knowledge_scope`、`tags`、`updated`）、H1–H6 标题块、`[[Wikilink]]`、`RUNBOOK/` 目录约定、看板文档。

2026-08-09 在本机（Windows，uv/Python 3.12+）实测（单次调用，冷启动后）：

| 操作 | 耗时 |
| --- | --- |
| 全库检索（45 处命中，44 文件全扫描） | ~72ms |
| 运行手册定位 | ~64ms |
| 读取首页 `个人平台总览.md` | ~1.4ms |
| 行动看板结构化解析 | ~1.3ms |

## 三个方案对比

### A. 按需扫描（现状，推荐）

- 每次请求扫描当前 Markdown，做标题块切分与确定性打分；
- 优点：零同步、零过期、实现与审计都简单，全库扫描在 100ms 量级；
- 缺点：检索是字面量匹配，没有同义/语义理解；文件量极大时线性退化。

### B. 轻量索引（倒排/标题缓存）

- 构建标题、标签、路径、链接的倒排表并缓存；
- 收益：在 44 文件规模下收益为零——扫描本身只需几十毫秒，索引反而引入"索引过期 vs vault 变化"的治理成本；
- 若未来文件量到 ~2k 且扫描超过可接受延迟，可先在 MCP 内部加只读缓存或倒排，不改工具契约。

### C. 完整 RAG（embedding + 向量库）

- 收益：同义表达、语义召回；
- 成本：embedding 模型与依赖、向量库（SQLite-vec/Chroma 等）、索引同步与过期治理、进程内常驻资源；
- 对本项目：vault 只有 44 个文件且结构已足够；现有检索已经能按标题/标签/链接/全文四维定位；引入 RAG 是"用更复杂的系统解决不存在的召回问题"。

## 结论与建议

**不实现 RAG，保持按需扫描。** 依据：

1. 规模：44 文件、全扫描 <100ms，远低于任何交互预算；
2. 结构：frontmatter 标签、Wikilink 与 `RUNBOOK/` 约定已经提供结构化入口，确定性检索够用；
3. 资源：本机个人使用，RAG 常驻模型与向量库的成本大于收益；
4. 一致性：无索引即无过期问题，与 ADR-0001 的"文档快照 ≠ 实时状态"边界一致。

何时重新评估（任一生效即触发）：

- vault 文件量增长到 ~2000 以上且全扫描超过 ~500ms；
- 出现被真实使用证明的召回失败（同义查询找不到既有文档），且无法通过加别名/标签解决；
- 部署方式变为跨机器或多用户（此时 HTTP + 服务化是更优先的问题）。

若触发，优先方案 B（MCP 内部轻量索引，接口不变），而不是直接上完整 RAG。
